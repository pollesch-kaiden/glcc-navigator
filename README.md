## Tech Stack

- **Expo + React Native** — cross-platform mobile app
- **TypeScript** — type safety throughout
- **MapLibre Native (v11)** — open-source map rendering
- **Protomaps** — vector tile hosting for the basemap
- **Zustand** — global state management
- **OpenStreetMap via Overpass API** — source data for POIs and paths
- **Custom A\* pathfinding** — on-device routing engine with no external routing API
- **expo-network** — detects WiFi vs. cellular connectivity before large downloads

## Adding and Editing POIs

POIs come from two sources that are merged automatically at runtime by `usePOIs.ts`.

| File | Purpose | Edit by Hand? |
|---|---|---|
| `glcc-pois-osm.json` | Auto-imported from OpenStreetMap | No — regenerated by script |
| `glcc-pois-custom.json` | Your enrichments and brand-new POIs | Yes — this is your file |

### Enriching an Existing OSM POI

Every OSM-imported POI has a stable `id`, such as `"osm-way/262908418"`. To add activities, amenities, accessibility information, or a description to an existing POI, find its `id` in `glcc-pois-osm.json`, then add a matching entry to `glcc-pois-custom.json` containing only the fields you want to add or override.

```json
{
  "type": "Feature",
  "geometry": {
    "type": "Point",
    "coordinates": [-89.0182293, 43.8160216]
  },
  "properties": {
    "id": "osm-way/262908418",
    "nearestNodeId": "node-773",
    "activities": ["sleeping", "dining"],
    "amenities": ["wifi", "restrooms"],
    "accessible": true,
    "hasStairs": false,
    "description": "57-room lodge near the Avenue of the Flags."
  }
}
```

> **Important:** Always keep the `nearestNodeId` field assigned by the linking script. Deleting it breaks routing to that POI. See [Re-Linking POIs After Path Changes](#re-linking-pois-after-path-changes).

Available `activities` values:

```text
swimming, kayaking, hiking, fishing, meetings, dining, sleeping,
sports, worship, nature, history, beach, bonfire, games, art, music
```

Available `category` values:

```text
lodging, dining, conference, recreation, landmark, restroom,
parking, waterfront, chapel, other
```

### Adding a Brand-New POI

For POIs that do not come from OSM, use an `id` prefixed with `custom-` so it never collides with an OSM ID. Provide a complete entry:

```json
{
  "type": "Feature",
  "geometry": {
    "type": "Point",
    "coordinates": [-89.0155, 43.8145]
  },
  "properties": {
    "id": "custom-volleyball-court",
    "name": "Sand Volleyball Court",
    "category": "recreation",
    "description": "Outdoor sand volleyball court, open to all guests.",
    "activities": ["sports"],
    "amenities": [],
    "accessible": false,
    "hasStairs": false,
    "nearestNodeId": "",
    "tags": ["outdoor", "sports"],
    "source": "custom"
  }
}
```

After adding a new POI, run the linking script to calculate its `nearestNodeId`:

```bash
npx ts-node scripts/linkPoisToGraph.ts
```

### Re-Importing Fresh OSM Data

If you re-run the Overpass query and `importOsmPois.ts`, your `glcc-pois-custom.json` enrichments are safe as long as the `id` values still match.

Never delete `glcc-pois-custom.json` without backing it up first.

### Finding Coordinates for New POIs

Use the built-in coordinate picker on the map screen:

1. Tap the reticle button in the bottom-right corner.
2. Pan the map until the fixed crosshair is over the desired location.
3. Copy the displayed `[lng, lat]` coordinates.
4. Paste the coordinates into the POI's `coordinates` field.

> **Tip:** For quick on-site edits without touching JSON files directly, the [In-App Admin Editor](#in-app-admin-editor) supports adding, editing, and deleting POIs — including picking coordinates on the map — straight from the app.

## Adding and Editing Paths

Paths currently come from OSM. A manually maintained custom-path file is planned for the future.

| File | Purpose |
|---|---|
| `glcc-paths.geojson` | Auto-imported from OSM highway ways |
| `glcc-paths-custom.geojson` | Future file for manually traced paths |

### Path Properties

Each path is a GeoJSON `LineString` with properties describing how it can be used.

```json
{
  "type": "Feature",
  "geometry": {
    "type": "LineString",
    "coordinates": [
      [-89.0180, 43.8160],
      [-89.0175, 43.8158],
      [-89.0170, 43.8155]
    ]
  },
  "properties": {
    "id": "osm-way/12345",
    "name": "Avenue of the Flags",
    "transportModes": ["walking", "biking", "golf_cart", "car"],
    "surface": "paved",
    "hasStairs": false,
    "bidirectional": true,
    "source": "osm"
  }
}
```

### Specifying Which Transport Modes Can Use a Path

The `transportModes` array controls exactly which travel modes can use a path segment.

| Path Type | `transportModes` Value |
|---|---|
| Walking trail only | `["walking"]` |
| Bike and walking path | `["walking", "biking"]` |
| Shared cart path | `["walking", "biking", "golf_cart"]` |
| Full road | `["walking", "biking", "golf_cart", "car"]` |

The A* routing engine only travels along edges where `transportModes` includes the user's selected transport mode.

### Making Paths Connect to Each Other

Paths automatically connect wherever their coordinates physically meet or come within **5 meters** of each other.

The graph generator, `generateGraph.ts`, treats every coordinate along every path as a potential node and merges nearby points into a shared node.

- If two paths cross or touch, they connect automatically.
- No manual linking is required when coordinates meet within 5 meters.
- If paths should connect but do not share coordinates within 5 meters, they are treated as disconnected graph islands.

After adding or changing paths, verify network connectivity:

```bash
npm run generate-graph
npx ts-node scripts/checkGraphConnectivity.ts
```

A healthy network should have almost all nodes in one large connected component. Small islands with only a few nodes are usually acceptable because they can represent genuinely isolated trails. Many small islands typically mean paths that should connect are not quite touching.

## Accessibility and Stairs

Stairs are marked at the **individual path segment level**, not on an entire building or path. This allows accessible routing to exclude only the segment that contains stairs while keeping other nearby routes available.

```text
Building A --path--path--[STAIRS]--path-- Building B
                            ^
                  hasStairs: true on this
                  segment only
```

### Marking Stairs in a Path

Set `"hasStairs": true` on the specific `LineString` segment where physical stairs are located.

```json
{
  "type": "Feature",
  "geometry": {
    "type": "LineString",
    "coordinates": [
      [-89.0168, 43.8175],
      [-89.0167, 43.8176]
    ]
  },
  "properties": {
    "id": "custom-chapel-steps",
    "name": "Chapel Steps",
    "transportModes": ["walking"],
    "hasStairs": true,
    "surface": "paved",
    "bidirectional": true
  }
}
```

### How This Affects Routing

When a user selects **"No, please avoid stairs"** during onboarding, `canUseStairs` is set to `false` in app state.

The A* algorithm then skips every graph edge where `hasStairs: true` and finds an accessible alternate route when one exists.

- Only the stair segment is excluded.
- All other paths connected to the nodes on either side of the stairs remain usable.
- If stairs are the only way to reach a destination, routing correctly returns **"No route found"** rather than silently routing through stairs.

If a destination should be wheelchair-accessible, add an alternate accessible route such as a ramp or elevator path.

## How Routing Works

The app uses a custom A* (A-star) pathfinding algorithm that runs entirely on-device. It does not require an internet connection or external routing API, which is important because GLCC has limited cell service in some areas.

### The Basic Idea

1. The campus path network is modeled as a graph.
2. Intersections and coordinate points become graph nodes.
3. Path segments between nodes become graph edges.
4. Each edge stores distance, allowed transport modes, surface type, and stair information.
5. When a user requests directions, A* starts at the graph node nearest their GPS location.
6. A* explores the most promising path first by using straight-line distance to the destination as a guide.
7. It filters out edges that do not match the selected transport mode or accessibility preference.
8. Once it reaches the destination node, it reconstructs the route and returns coordinates used to draw the route on the map.

This is the same fundamental routing approach used by many GPS navigation systems, except it runs locally on the phone rather than on a remote server.

## Multi-Modal Routing

Some destinations, such as building entrances, can only be reached using a short walking-only footpath. Users may not be able to drive, bike, or use a golf cart directly to the destination.

The app handles this with a realistic park-and-walk routing approach.

### How It Works

1. Try a direct route using the user's selected transport mode, such as `car`.
2. If a direct route fails, search outward from the destination along walking-only paths.
3. Find the nearest point where a road usable by the selected travel mode exists. This is the **gateway node**.
4. Route using the selected mode to the gateway node.
5. Route on foot from the gateway node to the destination.
6. If no gateway is found within the configured range, fall back to a full walking route so the user still receives a usable route when possible.

```text
Vehicle route:    Start ---- car/bike/cart ---- Gateway Node
                                                 |
                                                 | walking-only path
                                                 |
Destination:                                    Destination
```

### Visual Indication

The vehicle portion of the route is drawn as a solid green line.

The final walking approach is drawn as a dashed, lighter green line. For `car` mode, the POI card names the parking lot when one was found nearby:

```text
Park at North Lot, then walk to the destination.
```

or, when no named lot is found within range:

```text
Includes a short walk from parking.
```

This makes it clear where users should expect to stop driving, biking, or using a golf cart and continue on foot.

### Adjusting the Search Distance

The maximum distance searched for a gateway node is controlled in `src/routing/multiModal.ts`.

```typescript
export const MAX_GATEWAY_WALK_DISTANCE_METERS = 400;
```

Increase this value if legitimate destinations are being marked unreachable by vehicle. Decrease it if the suggested gateway points require users to walk farther than is reasonable.

### Named Parking Lot Pickup Points

For the `car` transport mode specifically, the gateway search prefers nodes near POIs with:

```typescript
category: "parking"
```

instead of a generic nearest point on a road. Parking lot POIs are added to `glcc-pois-custom.json` like any other custom POI, using `category: "parking"`.

If no named parking lot is found within `MAX_GATEWAY_WALK_DISTANCE_METERS`, the app falls back to the generic nearest-point behavior described above.

> **Note:** This parking-lot preference currently only applies to `car` mode. Bikes and golf carts continue to use the generic nearest-point gateway search, since smaller vehicles can realistically get closer to building entrances.

## Search and Filter Drawer

The hamburger menu icon in the top bar opens a left-sliding drawer for searching and filtering points of interest.

### Filtering by Activity or Category

The drawer groups filters into three collapsible sections: Activities, Categories, and Locations. Selecting one or more filters immediately narrows down which POI markers are shown on the map.

Filters use **OR logic** — selecting both "Swimming" and "Dining" shows POIs that match either activity, not only POIs that match both.

### Searching by Name

Typing in the search box filters across all three sections simultaneously and automatically expands any section containing a match. Tapping a location result in the drawer closes the drawer, flies the map to that POI, and opens its POI card.

### Adjusting Filter Options

Available activity and category values are defined in a single place:

```typescript
// src/utils/filterOptions.ts
export const ACTIVITY_OPTIONS = [ /* ... */ ];
export const CATEGORY_OPTIONS = [ /* ... */ ];
```

Adding a new activity or category value requires updating this file, plus adding a matching entry to the `POICategory` or `ActivityTag` type in `poi.types.ts` if the value should be type-checked.

## Offline Map Support

The app supports fully offline use once the campus map has been downloaded. This covers two separate layers.

- **Always offline, no action needed:** POI data, path data, and the routing graph are bundled directly in the app's JavaScript bundle. Routing and POI browsing work with zero internet connection, always.
- **Requires a one-time download on WiFi:** map tiles (roads, terrain, buildings) are downloaded via MapLibre's `OfflineManager` and cached locally. Until downloaded, the app requires an internet connection to display the visual map background.

### How It Works

`useOfflinePack` (`src/hooks/useOfflinePack.ts`) manages the download lifecycle:

- Checks for an existing offline pack on app launch.
- Exposes `downloadPack()` to start downloading, shown via `OfflineDownloadBanner` when no pack exists yet.
- Reports live download progress.
- Exposes `deletePack()` to remove the cached pack, guarded against being called while `status === 'downloading'` to avoid corrupting the offline database.

Packs are identified via a `metadata.packKey` value rather than a name field, since MapLibre's `OfflinePack` type has no built-in name property.

### Cellular Data Confirmation

Before starting a download, the app checks the current network type using `expo-network`. If connected via WiFi, the download starts immediately. If connected via cellular, a native-style confirmation prompt appears, similar to the App Store's own WiFi/cellular download prompt, letting the user choose **Wait for Wi-Fi** or **Use Cellular**. If there is no connection at all, the user is told to connect to WiFi or cellular first.

> **Note:** The download banner itself is shown regardless of connection type so users understand the map may stop rendering fully if they lose connectivity before downloading.

### Stall Detection and Recovery

If the network connection is lost mid-download, the native download can silently stop sending progress updates without ever firing an explicit error. A stall timer resets every time a progress update is received. If no progress update arrives within 15 seconds, the download is treated as failed:

- The pack status is set to `error` with a user-facing message.
- The partially-downloaded pack is automatically deleted so it cannot be left in a corrupted, half-downloaded state.
- The banner shows a Retry button, and tapping it starts a completely clean download rather than attempting to resume.

### Recovering From a Stuck or Corrupted Download

If a download ever appears stuck at 0 percent outside of the stall-detection scenario above (for example, from manually deleting a pack while it was actively downloading), the offline database can be fully wiped and reset with:

```typescript
import { OfflineManager } from '@maplibre/maplibre-react-native';
await OfflineManager.resetDatabase();
```

This clears all offline packs and ambient cache data, allowing a clean fresh download afterward.

### Testing Offline Behavior

Development builds always require a Metro connection to load JavaScript, so airplane mode testing will show a "No script URL provided" error regardless of whether tiles are cached. This is expected and unrelated to tile caching.

To properly test offline behavior, build a Release configuration:

```bash
npx expo run:ios --device --configuration Release
```

Only Release builds have JavaScript embedded directly in the app binary, matching what actually ships to users. Only in a Release build will airplane mode correctly test whether cached map tiles render offline.

## In-App Admin Editor

A hidden admin mode allows adding, editing, and deleting POIs directly from the app on a phone, without requiring a rebuild or code change. This is intended for finalizing POI data while physically on-site at GLCC.

### Unlocking Admin Mode

Tap the app version number on the Settings screen seven times, with each tap occurring within two seconds of the previous one. Repeating this locks admin mode back off.

> **Note:** The tap target is intentionally invisible — it looks like plain static text, not a button, so the gesture is not obvious to a regular user browsing Settings.

### How Admin Edits Are Stored

Admin edits are stored locally on the device only, in a separate persisted store (`src/store/useAdminStore.ts`), layered on top of the bundled `glcc-pois-osm.json` and `glcc-pois-custom.json` data at runtime. Deleting a POI does not remove it from the bundled files; it stores a tombstone entry (`{ id, deleted: true }`) that hides the POI everywhere in the app.

Admin edits made on one device are **not** automatically synced to any other device or to the codebase. See [Exporting Admin Edits](#exporting-admin-edits) below.

### Adding, Editing, and Deleting POIs

From the admin POI list screen:

- Tap any row to edit that POI's fields.
- Tap the "+" button to add a brand-new POI.
- Tap the trash icon on a row to delete it, after confirming.

The edit form supports name, category, activities, description, amenities, hours, accessibility, stairs, and coordinates.

### Picking a Location on the Map

Instead of typing coordinates by hand, tap "Pick on Map" in the POI form to overlay the coordinate-picker crosshair on the map. Pan the map until the crosshair is over the desired location, then confirm to return to the form with the new coordinates filled in and every other field preserved.

### Exporting Admin Edits

Because admin edits only live on the device that made them, they must be manually merged back into the codebase before they take effect for every user.

Use the export option on the admin list screen to:

1. Merge the bundled `glcc-pois-custom.json` data with every local admin edit into one complete file.
2. Open the native Share sheet so the merged file can be saved, AirDropped, or emailed.
3. Manually replace `glcc-pois-custom.json` in the codebase with the exported file, then commit the change.

> **Note:** This manual export/import workflow was chosen deliberately over a cloud backend, since a full backend is unnecessary infrastructure for a single-admin, non-profit project at this stage.

## MapLibre v11 API Reference

The MapLibre React Native library changed significantly around v11. Named imports replaced default or namespace imports, and several component and property names changed.

```typescript
import {
  Map,            // Map container; was MapView in older versions
  Camera,         // Controls the viewport
  UserLocation,   // Blue GPS dot
  GeoJSONSource,  // Supplies GeoJSON data to layers; was ShapeSource
  Layer,          // Renders line, circle, symbol, and fill layers
  Marker,         // Single interactive pin; uses lngLat, not coordinate
  ViewAnnotation, // Custom React view pinned to a map coordinate
} from '@maplibre/maplibre-react-native';
```

### Layer Types

```typescript
<Layer type="line" paint={{ 'line-color': '#000' }} />

<Layer type="circle" paint={{ 'circle-radius': 8 }} />

<Layer type="symbol" layout={{ 'text-field': 'Hello' }} />

<Layer type="fill" paint={{ 'fill-color': '#000' }} />
```

### `layout` vs. `paint` Properties

MapLibre layer properties are split into two categories.

```text
layout: structural properties that affect how geometry is shaped
  - line-cap
  - line-join
  - text-field
  - text-size
  - text-anchor
  - icon-image
  - icon-size
  - visibility

paint: visual properties that affect colors, opacity, and widths
  - line-color
  - line-width
  - line-opacity
  - circle-color
  - circle-radius
  - circle-stroke-color
  - text-color
  - text-halo-color
  - fill-color
  - fill-opacity
```

`line-cap` and `line-join` belong in `layout`, not `paint`. Putting them in `paint` is a common source of confusing TypeScript errors.

### Camera Bounds and Panning Restrictions

```typescript
<Camera
  initialViewState={{
    bounds: [west, south, east, north],
    padding: { top: 40, bottom: 40, left: 20, right: 20 },
  }}
  maxBounds={[west, south, east, north]}
  minZoom={1}
  maxZoom={19}
/>
```

### Inlining the Style Instead of Using a Hosted URL

To avoid style-loading network round trips and an iOS Simulator networking issue, the map style is constructed locally using `@protomaps/basemaps` rather than fetched from a hosted `style.json` URL.

```typescript
import { layers, namedFlavor } from '@protomaps/basemaps';
```

> **Version lock:** `@protomaps/basemaps` must remain aligned with the version used by the tile endpoint URL, currently v4. If this package is upgraded, verify whether the tile endpoint must also be updated, such as from v4 to v5.

> **Note:** `OfflineManager.createPack` specifically requires a fetchable URL string for `mapStyle` rather than the inlined style object, since it needs to actually download and cache resources natively. A separate `PROTOMAPS_STYLE_URL` constant is kept in `mapStyle.ts` for this purpose alongside the inlined `MAP_STYLE` object used for live rendering.

## Known Issues

### iOS Simulator Tile Loading Timeouts

The iOS Simulator can intermittently encounter networking errors such as:

```text
NSURLErrorDomain -1001
NSURLErrorDomain -2103
```

These can cause Protomaps tile or style requests to time out even when the same requests work through `curl` or on a physical device.

This is not typically caused by the API key, application code, or Protomaps servers. It is specific to the iOS Simulator's CoreSimulator networking behavior.

Map tiles, POIs, and routing work reliably when tested on a physical iPhone.

Possible workarounds:

- Reboot the Mac to clear the stalled networking daemon.
- Disable VPN or proxy software, including Little Snitch, Charles Proxy, or a corporate VPN.
- Erase the Simulator:

```bash
xcrun simctl erase all
```

- Prefer testing map-related functionality on a physical device.

### Metro Binding to Localhost Instead of LAN IP

When testing on a physical device, Metro can sometimes bind only to `localhost` instead of the Mac's LAN IP address. This prevents the phone from reaching the Expo development server.

Start Expo with LAN mode enabled:

```bash
npx expo start --dev-client --lan
```

### Metro Unreachable Over Cellular Data

During development, if the phone switches from WiFi to cellular data, it can no longer reach the Metro dev server running on the Mac's local network. This produces extensive native networking logs and a "No script URL provided" or "Cannot connect to Expo CLI" error. This is expected and only affects development builds; it does not indicate a problem with the app itself. Reconnect to the same WiFi network the Mac is on to resolve it.

## Development Workflow

| Task | Command |
|---|---|
| Daily JavaScript/UI development, with app already installed | `npx expo start --dev-client --lan` |
| First-time install or after installing a new native package | `npx expo run:ios` for Simulator, or `npx expo run:ios --device` for a physical device |
| Testing true offline behavior (map tiles, no Metro connection) | `npx expo run:ios --device --configuration Release` |
| Changed `app.json` settings such as icon, splash screen, or permissions | `npx expo prebuild --clean`, then rebuild |
| Re-imported OSM data | Run import scripts, generate the graph, then re-link POIs |
| Added or changed paths | `npm run generate-graph`, then `npx ts-node scripts/linkPoisToGraph.ts` |

### Re-Linking POIs After Path Changes

Whenever the path network changes, graph node IDs can shift. This includes adding paths or re-running graph generation.

Always run the POI linking script after path changes:

```bash
npx ts-node scripts/linkPoisToGraph.ts
```

This recalculates `nearestNodeId` for every POI and writes the results into `glcc-pois-custom.json`.

Custom enrichment fields such as `activities`, `amenities`, and `description` are preserved as long as their POI `id` values still match.

### Full Data Pipeline

When updating data from OpenStreetMap, export fresh POI and/or path data from Overpass Turbo and save it to:

```text
assets/map/osm-import/
```

Then run the full pipeline in this order:

```bash
# 1. Convert raw OSM exports to application data files
npx ts-node scripts/importOsmPois.ts
npx ts-node scripts/importOsmPaths.ts

# 2. Rebuild the routing graph
npm run generate-graph

# 3. Verify graph connectivity
npx ts-node scripts/checkGraphConnectivity.ts

# 4. Re-link every POI to its nearest graph node
npx ts-node scripts/linkPoisToGraph.ts
```
